# Sprint 43 — Real Foundry IQ + Fabric IQ Grounding — Design

> Produced via the Superpowers `brainstorming` skill, following live UI
> testing of every Copilot agent against real SIT infrastructure
> (`appsit.curavias.ch`) after Sprint 42's Product Owner Agent remediation.
> User confirmed scope interactively over several rounds of real Q&A.

## 1. Context

Sprint 42 proved the **Product Owner Agent** is genuinely grounded
end-to-end on real SIT infrastructure (`refused: false`, real citations,
6,333 real indexed documents). Testing the **rest of the platform** — the
8 agent-host-registered specialized agents (`bmca`, `ooa`, `dca`, `orsa`,
`sba`, `csa`, `data-quality`, `onboarding`) and every Main-pane board —
found the opposite: every one of them is currently backed by hardcoded
mock/fixture logic, not real Foundry or Fabric data, despite looking "live"
in the UI.

### 1.1 Root-cause evidence (from live testing + code reading)

| Layer | File | Finding |
| ----- | ---- | ------- |
| Chat/synthesis | `apps/hcc-agent-host/src/api/app.py:116` | `chat_model=MockChatModel()` — hardcoded, unconditional, every environment. No real Foundry-chat-model implementation exists anywhere in `hcc-agent-host`. |
| Table grounding (fallback) | `apps/hcc-agent-host/src/tools/fabric_adapter.py` | `HostState.__init__` never passes a `query_fn`, so every `FabricAdapter.query(table)` call returns a **hardcoded 3-row dict** (`gold.bed_assignment`, `gold.fact_capacity_baseline`, `gold.discharge_score` only) or `[]` for any other table. |
| Board data | `apps/hcc-agent-host/src/golden/service.py` | `/golden/{resource}` reads static `golden/data/*.json` fixture files. Own docstring: *"This is the seam that lifts to live Fabric RLS in #424 M4 without an app change"* — the lift was never done. |
| Data Agent grounding (the one real path) | `apps/hcc-agent-host/src/tools/fabric_data_agent_client.py` + `_build_live_data_agent()` | **Real** when `FABRIC_DATA_AGENT_*` env vars are set (they are, on the real `ca-agent-host-ihzhhpf-sit`) — used only for manifests with `groundingAgent: primary` binding, and only for retrieval; synthesis downstream is still always the mock. |

**Empirical confirmation:** `bmca-agent`'s live answer ("Auslastung Station
B liegt bei 92%...") is `fabric_adapter.py`'s hardcoded
`{"ward": "B", "occupied": 46, "capacity": 50}` (46/50 = 92%) verbatim. The
other 5 agents' tables aren't in that dict, so grounding is empty and
`MockChatModel` returns its "no data" fallback — confirmed live for `ooa`,
`orsa`, `sba`, `dca`, `csa`.

### 1.2 Why this matters

The user's own framing: *"this is key to success of the whole solution to
show how we get the real data from Foundry IQ and Fabric IQ driving the
patient flow successfully."* A more articulate chat model summarizing the
same hardcoded 3-row dict does not deliver that — grounding and synthesis
are both in scope, together.

## 2. Goals

1. Every specialized agent's chat answer is generated by a real Foundry
   model call, not `MockChatModel`.
2. Every specialized agent's grounding (and every board's data) comes from
   real Fabric Gold data (via the Data Agent or an equivalent live query
   path), not hardcoded dicts or static JSON fixtures.
3. A real, end-to-end UI test proves the full loop: user clicks a context
   element (a board row, a signal, a recommendation) → that context is
   passed to the agent → the agent returns a real, grounded, cited answer
   — for every agent, not just the Product Owner Agent.
4. Every degradation (missing data, model failure) is honest and visible
   (existing `GroundingNotice`/`provenance` badge pattern), never silent.

## 3. Non-goals

- Changing the manifest-driven system-prompt assembly, the redaction
  layer, the audit/persistence layer, or the HITL approval gate — none of
  these are implicated by the findings above; they stay as-is.
- PROD promotion of any of this work — SIT only, per the platform's
  standing convention this whole session.
- Building a new Foundry Agent registration pipeline — the 8 agents are
  already registered (`register_decision_tier.py`/`live_factory.py`);
  WS-1 only changes how `hcc-agent-host` *invokes* them (or an equivalent
  model), not how they're registered.

## 4. Workstreams

### WS-1 — Real chat/synthesis (replace `MockChatModel`)

**Decision deliberately deferred** (user's explicit instruction) — three
approaches are documented in full; WS-1's first task is a short, timeboxed
decision spike, not a fresh design debate.

| | **A — Invoke the registered Foundry Agents** | **B — Direct Azure OpenAI chat completions** | **C — Hybrid (Assistants-style run loop against the registered Agents)** |
| - | - | - | - |
| Mechanism | `POST .../projects/.../agents/{name}` create-thread → run → poll (Foundry Agent Service, `2025-05-15-preview`) | Single synchronous `POST .../openai/deployments/{model}/chat/completions` on `ai-ihzhhpf-sit-eastus2.openai.azure.com` | Same create-thread/run/poll shape as `fabric_data_agent_client.py`, pointed at the registered Agents instead of a plain deployment |
| RBAC | **New grant needed**: `Foundry User` or `Foundry Project Manager` on `ai-ihzhhpf-sit-eastus2` (confirmed via `live_factory.py`'s own docstring: `Cognitive Services User` returns 401 on this API) | **None** — agent-host's MI already has `Cognitive Services User` on this account (confirmed, `sit-evidence-2026-07-17.md`) | Same new-grant requirement as A |
| New code | A full invocation client (create/run/poll) — none exists today, only *registration* code (`live_factory.py`) does | Reuses the exact client shape already built + live-tested for `po-agent-service` this session | Reuses `fabric_data_agent_client.py`'s proven poll loop shape, re-pointed |
| Uses the 8 registered Agent objects as first-class entities | Yes | No — the registration's own metadata (a `decision_tier_coordination` function tool + role tag) isn't needed for plain Q&A; `hcc-agent-host` already assembles system prompt + grounding client-side per manifest | Yes |
| Latency | Slower (thread + run + poll) | Fastest (single call) | Slower (thread + run + poll) |
| Risk | New RBAC + new untested protocol code | Lowest — proven pattern, proven RBAC | New RBAC; untested protocol code, uncertain payoff vs. A |

**User's stated preference:** A — the concern with B is that it mirrors
the Product Owner Agent's own pattern too closely, which is itself
Foundry-IQ-search-centric (Class A corpus) with the Fabric-grounded slice
(BVA/Class C reconciliation) not yet proven end-to-end either. A exercises
the platform's actual registered multi-agent surface, which is the part of
the story this sprint needs to prove.

**WS-1 Task 0 (decision spike, timeboxed):** grant `Foundry User` to
agent-host's MI on `ai-ihzhhpf-sit-eastus2`; build a minimal `create
thread → post message → run → poll → read response` script against one
registered agent (e.g. `bmca-agent`) mirroring `fabric_data_agent_client.py`'s
proven shape; confirm it returns a real, non-mock answer. If this works
within the timebox, proceed with **A** for all 8 agents. If it doesn't
(auth issue, protocol mismatch, agent definition doesn't behave as
expected for plain Q&A), fall back to **B**, already de-risked. Document
the outcome as a short ADR-style decision record before continuing WS-1's
remaining tasks.

### WS-2 — Real Fabric grounding (replace `FabricAdapter`'s hardcoded dict)

Wire a live `query_fn` into `FabricAdapter` for every manifest's grounding
tables (`gold.or_schedule`, `gold.staff_schedule`, `gold.discharge_candidates`,
`gold.crisis_signals`, `gold.fact_occupancy_forecast`, etc. — not just the
3 currently hardcoded). Two candidate mechanisms, both already proven
elsewhere in this repo:
- Extend the existing Fabric Data Agent binding (already real, already
  working) to cover every manifest, not just `groundingAgent: primary`
  ones — mirrors exactly how Sprint 42 wired Class A/D for the PO agent.
- Or a direct Fabric SQL/KQL query surface (`fabric-mcp`'s own `query`
  tool, already the documented contract `FabricAdapter.invoke()` expects)
  if a Data Agent binding per-table proves too heavy.

This workstream **should land before or alongside WS-1**, not after: a
real chat model summarizing the same hardcoded rows is not the improvement
the user asked for.

### WS-3 — Real board data (`/golden/{resource}` → live Fabric-backed RLS)

Complete the already-designed `#424 M4` seam: swap `SimulatedRlsProvider`
(reads `golden/data/*.json`) for a live provider that queries real Fabric
Gold tables through the same connection WS-2 establishes, preserving the
existing RLS/deny-by-default contract and the `_rls` provenance metadata
every board already reads.

### WS-4 — End-to-end click-to-answer UI test (closes the loop)

A real Playwright test suite (per the repo's existing pattern in
`apps/hcc-app-fluent/tests/e2e/`) that, for every board and every agent:
1. Navigates to the board.
2. Clicks a real context element (a table row, a signal card, a
   recommendation) — the existing "Click a row → Copilot actions" affordance
   already visible in the UI.
3. Confirms the clicked context is actually passed into the agent panel
   (not just a generic open).
4. Sends a follow-up question and asserts the response is `refused: false`
   (or an honestly-disclosed `simulated`/degraded state, never a silent
   fabrication) with real citations.
5. Repeats for the Start/Backstage Product Owner Agent (already proven
   working after Sprint 42 + the `PO_AGENT_URL` fix) as the regression
   baseline every other agent is measured against.

This is the acceptance test for WS-1/2/3 together — it does not pass
until all three land for a given agent.

## 5. Sequencing recommendation

WS-2 (real grounding) first or in parallel with WS-1 (real synthesis) —
synthesis without real grounding doesn't deliver the goal. WS-3 (board
data) can run in parallel with WS-1/2 since it's a separate read path
(`/golden/*` vs. the chat grounding path), though it converges on the same
underlying Fabric connection. WS-4 runs last per agent, as each of the
other three lands for that agent, and again as a full regression pass at
the end.

## 6. Verification gates

- Existing `evals/<agent>/` golden-task suites re-run against real
  responses, not mock, for every agent touched.
- Live re-test via raw HTTP (mirrors Sprint 42's evidence style) for at
  least one representative question per agent.
- WS-4's Playwright suite green for all 8 specialized agents + PO agent.
- No change to the redaction/audit/HITL layers — confirmed by their
  existing test suites staying green, untouched.

## 7. Risks / open items

- **WS-1's approach decision is explicitly open** — this design documents
  all 3 options with enough detail to execute the Task 0 spike, but does
  not commit to one. The spike's outcome must be recorded before WS-1's
  remaining tasks are planned in detail.
- **Per-agent grounding table coverage (WS-2) is not yet fully inventoried**
  — this design lists the tables observed during live testing; a full
  per-manifest audit of `grounding_tables` is needed as WS-2's first task.
- **RBAC for WS-1 Option A** is a real, not-yet-granted permission — needs
  the same `approved-to-apply` discipline as every other IAM change this
  session.
- **Scope is large.** Four workstreams, at least 8 agents, 7 boards. This
  design deliberately keeps them as one coherent initiative (they share
  the same root cause and the same Fabric connection) but the
  implementation plan should decompose them into independently
  deployable, delegable tasks (see the companion plan and GitHub issue).

## 8. Traceability

- Builds directly on Sprint 42's proven pattern
  ([`2026-08-08-sprint-42-po-agent-sit-remediation-design.md`](2026-08-08-sprint-42-po-agent-sit-remediation-design.md))
  — same Fabric Data Agent connection, same live-verification discipline.
- No new `FR-*`/`NFR-*` IDs — closes gaps against the existing agent-host
  (Sprint 13 T5) and golden-read (#424 M2/M4) requirement families.
