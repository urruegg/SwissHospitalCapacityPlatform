## Purpose and scope

Operator procedure to land the synthetic Curavias organisation-spine +
skills-evidence extracts into the WS-A1 ADLS Gen2 landing container, then run the
on-demand Bronze->Silver->Gold pipeline. Sprint 23 WS-A2 (issue #255), grounding
design **D5**.

> **Synthetic, no-PHI only.** Every file uploaded here is generated by
> `data/master-data/curavias-org-skills/generate_master_data.py` or the WS-B
> `skills_evidence_synth.py` seeder. Never place real worker or patient data in
> this container.

Ingestion runs as **Azure Container Apps Jobs** (WS-A3), never as a GitHub
workflow. This runbook is the manual/operator equivalent used for first-load and
verification.

## Prerequisites

* WS-A1 deployed (`stmasterdata<suffix>` + `landing` filesystem).
* WS-A2 OneLake shortcut created (`infra/modules/data-foundation/masterdata-landing/onelake-shortcut.md`).
* Caller holds **Storage Blob Data Contributor** on the landing account (the
  pipeline MI has this via WS-A1; a human operator needs it granted explicitly).
* `az` logged in to the SIT subscription; `python` (not `python3`) on PATH.

## Folder convention

```text
landing/curavias-org-skills/<source>/<yyyy-mm-dd>/<table>.csv
```

`<source>` in `{ successfactors, lms, skills-manager, work-id }`.

## Step 1 — Generate the synthetic extracts

```bash
python data/master-data/curavias-org-skills/generate_master_data.py
python data/master-data/validate_master_data.py
```

The validator must print `OK` before upload (silver-gate contract, design D5).

## Step 2 — Upload to the landing container

Parameterise every ID; nothing is hard-coded. `${...}` are shell variables the
operator sets per environment.

```bash
account="stmasterdata${SUFFIX}"          # e.g. stmasterdataihzhhpfsit
source="successfactors"                   # or lms | skills-manager | work-id
day="$(date -u +%Y-%m-%d)"

az storage fs directory upload \
  --account-name "${account}" \
  --file-system landing \
  --source "data/master-data/curavias-org-skills" \
  --destination-path "curavias-org-skills/${source}/${day}" \
  --recursive \
  --auth-mode login
```

Repeat per `<source>` that the run produced. `--auth-mode login` forces
Entra/RBAC auth (shared-key is disabled on the account by design).

## Step 3 — Run the on-demand pipeline

The Bronze->Silver->Gold flow is driven by the medallion notebooks over the
OneLake shortcut. Trigger the WS-A3 Container Apps Job (preferred) or run the
notebooks directly against the lakehouse. Upload to OneLake, when needed, uses
the shared helper (parameterised, consistent with `upload_to_onelake.py`):

```bash
python data-platform/scripts/upload_to_onelake.py \
  --workspace-id "${FABRIC_WORKSPACE_ID}" \
  --lakehouse-id "${FABRIC_LAKEHOUSE_ID}" \
  --source-root "data/master-data/curavias-org-skills" \
  --target "landing/curavias-org-skills/${source}/${day}"
```

## Step 4 — Verify

1. `az storage fs file list --account-name "${account}" --file-system landing --path "curavias-org-skills/${source}/${day}" --auth-mode login` lists the uploaded CSVs.
2. In the lakehouse, the OneLake shortcut surfaces the same folder under
   `Files/landing/curavias-org-skills/` (see the shortcut doc's Verify section).
3. The Silver gate quarantines any row that fails the org/skills contract
   (validated locally by `data/master-data/validate_master_data.py`).

## Rollback

Landing data is append-only per `<yyyy-mm-dd>` folder; to discard a bad load,
delete only that dated folder:

```bash
az storage fs directory delete \
  --account-name "${account}" --file-system landing \
  --path "curavias-org-skills/${source}/${day}" \
  --auth-mode login --yes
```

Deleting a dated folder is destructive; per
[AGENTS.md §4](../../AGENTS.md#4-confirmation-rule-for-deploy--delete) an
operator performs it explicitly — the pipeline never deletes landed data.
