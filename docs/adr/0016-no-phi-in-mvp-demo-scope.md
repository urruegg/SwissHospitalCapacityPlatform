## Context

The AMA SD Review already established that the platform operates on the Hospitalisation Episode as the control unit, not the patient, and uses pseudonymised identifiers only. That review however was prose-level guidance. ADR-0014 §2 and ADR-0013 §Decision-2 both restate "synthetic only" but the underlying principle — that the demo scope **must not contain any PHI or patient-sensitive data**, ever — has never been captured as its own ADR. Sprint 09 v2.0.0 introduces a live event-stream simulator and multiple data agents; formalising this principle now prevents drift (e.g. someone adding a "real patient sample" to test a corner case).

**Promoted Proposed→Accepted 2026-07-24** on OWNER confirmation of the no-PHI / metadata-driven posture (F2).

## Decision

In the demo scope (as defined by ADR-0013):

1. **No PHI** — no personal health information, no direct patient identifiers, no indirect combinations that could re-identify (birth date + postal code + admission date pattern). Every dataset in `bronze/`, `silver/`, `gold/`, every event on Event Hubs, every payload consumed by any agent, and every dashboard field is either fully synthetic (generated by the simulator) or pseudonymised reference data (dim_hospital / dim_specialty style, no persons). The control unit is the **Hospitalisation Episode**, not the patient; the platform is **metadata/episode-driven** and holds no direct or indirect patient identifiers (confirmed fact F2, 2026-07-24).

2. **Enforced at four gates** (each detailed below):

#### Gate 1: CI schema gate

Every `dc-*.schema.json` under `data/synthetic/schema/` sets `_pseudonymisation_flag=true` explicitly (existing pattern from `dc-demand-encounter-v1`); a new `policy/policy_gate.py` check refuses to merge a schema that lacks or falsifies this flag in the demo-scope profile.

#### Gate 2: Ingestion gate

Silver notebook validation (per Sprint 09 v1.0.0 draft §2.2) rejects rows where PII patterns are detected (regex checks for email, phone, DOB, CH AHV-13 numbers).

#### Gate 3: Agent gate

Every Foundry / Fabric agent prompt refuses to accept or emit PHI-shaped tokens; agent evals include a refusal fixture.

#### Gate 4: Dashboard gate

Power BI report may not surface any field whose semantic-model column carries a `phi=true` tag (protected via row-level security empty-set policy).

3. **Scope discipline** — this ADR is scoped to the demo scope only. It does **not** authorise the platform to process PHI in any other scope. When a future PROD deployment introduces PHI in Switzerland, ADR-0003/-0004/-0006 remain in force and this ADR does not need supersession — it simply doesn't apply to that scope.

## Consequences

**Positive:**

- Turns a well-known-but-informal principle into an enforceable one.
- Provides a clear stop-sign for future contributors who might otherwise add "just a little real data" for testing.
- Simplifies compliance evidence (one clear ADR to cite in audit).

**Negative:**

- Slight development friction — the simulator + all fixtures must be genuinely synthetic. Pseudonymisation rules (already in place per DC-DEMAND-ENCOUNTER-v1) are already synthetic-safe, so friction is minimal.

**Governance actions triggered by this ADR:**

- Update `docs/COMPLIANCE.md` addendum.
- Update `docs/SECURITY.md` §Data plane.
- Add the four gate checks to `docs/TEST.md`.

## Review triggers

Re-open this ADR when any of the following occurs:

1. A PROD Swiss deployment is proposed — ADR-0003/-0004 govern that scope, not this one.
2. A customer requests a synthetic dataset that mimics real patterns *too closely* and re-identification risk emerges — this ADR would tighten (add k-anonymity constraints).
3. The simulator is repurposed for a non-demo use — this ADR is scope-checked before that use is authorised.
